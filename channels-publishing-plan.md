### 1.2 Архитектура (спек §1 — «реализовать до каналов»)

| Требование спека | Реально в коде | Вердикт |
|---|---|---|
| **Канонический контент-объект** (hook/body/long_text/media/links/styling/overrides) | Нет. Везде гоняется сырая строка `digest.content` | ❌ ключевой gap |
| **Слой нормализации формата** (per-platform рендер) | Зачаток: нарезка 4096 внутри TG-паблишера. Логика размазана по паблишерам | ❌ |
| **Два тракта sync/async** | Всё — один код-путь: последовательные await в `publishDigest()` | ❌ |
| **FSM + очередь + воркер для async-тракта** | Нет. `queue-manager.js` — это очередь *статей на дайджест*, не публикаций | ❌ |
| **Публичный media-хостинг** (для IG/Threads) | Нет. Дайджесты чисто текстовые | ❌ (блокер для IG) |
| **Управление токенами** (refresh flows, ~60 дней Meta, ротация) | Нет. Статические токены в `.env`/`data/settings.env`. FB Page-токен — постоянный (`expires_at=0`), поэтому пока не болит | ⚠️ станет блокером на IG/Threads/LinkedIn |
| **Ретраи / exponential backoff (429/401/400)** | Нет. Ошибка → `console.error` → `null`, молчаливая потеря | ❌ |
| **Учёт публикаций** | Плоские колонки `facebook_post_id`/`telegram_message_id`/`youtube_post_id` в таблице `digests` — не масштабируется на 5+ каналов и не хранит статус/ошибки/ретраи | ❌ нужна таблица `publications` |
| **Poll-механика контейнеров** (IG/Threads) | Нет | ❌ (входит в async-тракт) |

### 1.3 Что уже есть сверх спека (переиспользуем)

- **Дашборд, таб «Публикация»** (`pro/public/syndication.html`) + `source_posts` ingest (browserless FB-чтение) — готовая витрина для статусов публикаций.
- **Auth-модель** read-public / write-auth — publish-эндпоинты уже защищены.
- **`src/services/llm.js`** — общий `callModel`, пригодится если понадобится генерация hook/обложек.
- **Модуль модерации** (FB+TG) — обслуживание последствий публикации уже есть для 2 каналов.
- **Open-core** структура (`src/pro/`) — решить: паблишеры новых каналов кладём в публичную часть или в pro (см. §4, вопрос В-1).

### 1.4 Важный контентный gap, которого нет в спеке

**Instagram не умеет text-only постов.** Дайджест — чистый текст, а IG требует хотя бы одно изображение/видео по публичному URL. Значит, подъём IG требует не только API-обвязки, но и **генерации обложки** (картинка с заголовком дайджеста / шаблонная карточка). Это отдельная задача этапа 3. Для X, Threads, LinkedIn текст самодостаточен.

## 2. Порядок этапов

Следует спек-§11, с поправкой: перед каналами — фундамент (спек §1 прямо требует «реализовать до каналов»). Каждый этап — независимо отлаживаемая единица со своими критериями приёмки. Существующие FB/TG не ломаем: они оборачиваются в новую архитектуру с сохранением поведения (легаси не рубим).

```
Этап 0. Фундамент (канонический объект, publications, ретраи)   ← только агент
Этап 1. X (Twitter)                                              ← самый быстрый канал
Этап 2. Threads                                                  ← Meta-обвязка, App Review
Этап 3. Instagram                                                ← та же обвязка + медиа-хостинг + обложки
Этап 4. LinkedIn (личный профиль)
Этап 5. Опционально: LinkedIn org / YouTube видео / TikTok / подкаст
```

**Почему Threads раньше Instagram** (отступление от спека, который ставит IG в первую волну): X + Threads — текстовые, публикуют дайджест как есть. IG требует медиа-хостинг + генерацию обложек — самый тяжёлый контентный довесок. Meta App Review подаётся один раз на оба scope (IG + Threads) — владелец проходит гейт единожды, а код поднимаем в порядке «дешевле → дороже». Если владелец хочет IG раньше — этапы 2 и 3 переставляются без потерь.

## Этап 0 — Фундамент публикации (без новых каналов)

**Цель:** архитектурная база из спек-§1, существующие FB/TG переведены на неё без изменения видимого поведения.

**[Агент] — всё сам, санкция владельца только на прод-деплой:**

1. **Таблица `publications`** (миграция идемпотентная, `CREATE TABLE IF NOT EXISTS`):
   `id, digest_id, platform, status (pending → container_created → media_uploaded → processing → published / failed), attempt_count, last_error, external_post_id, external_url, payload_json, created_at, updated_at`.
   Старые колонки `facebook_post_id`/`telegram_message_id` не удалять (читаются дашбордом) — писать в обе точки до конца миграции UI.
2. **Канонический контент-объект** (модуль `services/content-object.js`):
   `{ hook, body, long_text, media[], links[], styling[], overrides{} }`.
   Билдер из дайджеста: `hook` = первые строки/заголовок (≤175), `body` = текст ≤ короткого лимита, `long_text` = полный дайджест. На первом этапе `hook` строится эвристикой; опция «hook генерирует модель» — отдельный тумблер позже.
3. **Слой нормализации** (`services/render/{platform}.js`): канонический объект → валидный payload площадки. Существующая TG-нарезка 4096 переезжает сюда.
4. **Интерфейс паблишера** (контракт): `publish(canonicalObject, config) → { externalId, url } | throws TypedError`. FB/TG адаптируются под контракт (поведение бит-в-бит, регресс ловим тестами).
5. **Sync-тракт:** прямой вызов с ретраями — exponential backoff (1s/2s/4s, максимум 3 попытки) на 429/5xx; 4xx кроме 429 — не ретраить, фиксировать в `publications.last_error`.
6. **Async-тракт (каркас):** воркер-цикл поверх `publications` (интервальный тик, как у digest-очереди) — FSM-переходы, poll контейнеров, ретраи на каждом переходе. На этапе 0 воркер существует и тестируется на моке; первый реальный потребитель — Threads (этап 2).
7. **Дашборд:** таб «Публикация» показывает строки `publications` (канал / статус / попытки / ошибка / ссылка).
8. **FB Page:** поднять версию Graph API с v19.0 до актуальной (сверить по докам, спек говорит v25.0).
9. **Тесты** на: билдер канонического объекта, нормализаторы (границы обрезки), FSM-переходы, backoff, идемпотентность (повторная публикация того же дайджеста в тот же канал не дублирует пост — проверка по `publications`).

**[Владелец]:**
- Санкция на прод-деплой этапа 0 (поведение FB/TG не меняется — деплой низкорисковый).

**Критерии приёмки:** тесты зелёные; на проде дайджест публикуется в FB+TG через новый тракт; в `publications` — записи со статусами; сбой сети → ретраи → корректный `failed` с ошибкой, виден в дашборде.

## Этап 1 — X (Twitter)

**Гейта нет, только оплата. Самый быстрый канал.**

**[Владелец]:**
1. Завести/подтвердить **X Developer account** (на аккаунте, с которого постим; Premium на аккаунте уже есть — даёт длинный лимит ~25k, лонгрид одним постом).
2. В **Developer Console**: создать приложение, **купить кредиты** (pay-per-use; ориентир ~$0.015/пост, чтение дороже — точные ставки агент сверит). Решить месячный бюджет.
3. Прогнать OAuth 2.0 авторизацию (агент подготовит одноразовый локальный flow — открыть ссылку, подтвердить доступ).
4. Санкция на прод-деплой.

**[Агент]:**
1. **`[VERIFY]`-проверка перед кодом:** актуальные ставки per-endpoint, rate limits, лимит длины для Premium через API — по живой документации (спек-§12).
2. OAuth 2.0 user-context: одноразовый скрипт получения refresh-токена + автообновление access-токена в токен-модуле.
3. `publishers/x.js` (sync-тракт): `POST /2/tweets`. **Ссылка на источник — не в тело, а первым ответом-к-себе** (reply к только что созданному посту) — уходим от $0.20-сурчарджа и даунранка. Это два вызова API на публикацию.
4. Нормализатор: `hook` — первой строкой; лонгрид одним постом (Premium-лимит), fallback-обрезка если лимит не подтвердится.
5. Конфиг-ключи + секция в настройках дашборда + тумблер канала.
6. Тест на живом аккаунте (1 пост, затем удалить), деплой после санкции.

**Критерии приёмки:** дайджест уходит в X одной кнопкой/автоматом; ссылка в первом реплае; запись в `publications`; стоимость поста видна в логе.

## Этап 2 — Threads

**Пристёгивается к Meta-обвязке. Текстовый, лонгрид до 10 000 симв во вложении — дайджест влезает без нарезки.**

**[Владелец]:**
1. Убедиться, что есть **Instagram-аккаунт** (Threads-профиль привязан к IG) и он **Professional** (Business/Creator) — это же понадобится этапу 3.
2. В **Meta for Developers**: в существующем приложении (то, что для FB Page) включить продукт Threads. Если техтребования заставят — завести отдельное приложение (агент скажет по факту).
3. **Meta App Review** — главный гейт. Подать на scope Threads-публикации **и сразу на `instagram_content_publish`** (одно ревью на оба канала — рычаг из спек-§10). Владелец записывает скринкаст использования, заполняет формы (агент готовит черновики текстов и инструкцию записи).
4. Прогнать OAuth-авторизацию Threads (агент подготовит flow).
5. Санкция на прод-деплой.

**[Агент]:**
1. **`[VERIFY]`:** актуальная версия Threads API, лимиты вложения (10k), лимит ссылок (≤5), rate (250/сутки).
2. Токен-модуль: long-lived токен ~60 дней + **автоматический refresh** (крон-тик воркера, алерт через ntfy при провале обновления). Это первая реальная эксплуатация refresh-механики — FB-токен постоянный и её не требовал.
3. `publishers/threads.js` (async-тракт, первый реальный потребитель FSM): контейнер `media_type=TEXT` + `text_attachment.plaintext` (лонгрид) → poll → `threads_publish`.
4. Нормализатор: `hook` ≤175 в `text` (спек-§5), полный дайджест в `plaintext` вложения; **счётчик ссылок ≤5** (уникальные URL в text + вложении) — при переборе резать ссылки из хвоста и логировать; перехват `THREADS_API__LINK_LIMIT_EXCEEDED`.
5. Опционально `text_with_styling_info` (болд заголовков) — вторая итерация, не блокер.
6. Тесты, деплой после санкции.

**Критерии приёмки:** дайджест уходит в Threads (hook в ленте, лонгрид во вложении); FSM-статусы в `publications`; лимит ссылок соблюдается автоматически; refresh токена отработал хотя бы раз (или протестирован форсом).

## Этап 3 — Instagram

**Той же Meta-обвязкой, но два тяжёлых довеска: публичный media-хостинг и генерация обложек.**

**[Владелец]:**
1. Привязать IG Professional аккаунт к FB Page (если ещё не).
2. App Review уже подан на этапе 2 — дождаться одобрения `instagram_content_publish`.
3. **Выбрать вид обложки** (одно решение из вариантов, которые подготовит агент: шаблонная карточка с заголовком / AI-генерация / статичная брендовая картинка).
4. Санкция на прод-деплой.

**[Агент]:**
1. **Media-хостинг:** вариант-кандидат — раздача с собственного VPS (traefik уже терминирует TLS на `news.questtales.com`; статичный маршрут `/media/*` из тома). Проверить `[VERIFY]` требования IG к публичному URL (доступность на момент cURL, таймауты обработки). Если требования не пройдут — S3-совместимый bucket (решение эскалируется владельцу, т.к. это новый платный сервис).
2. **Генерация обложки:** рендер карточки 1080×1350 (4:5) с заголовком/номером дайджеста (серверный рендер: satori/canvas/шаблон — выбор за агентом). Файл кладётся в media-том → публичный URL.
3. `publishers/instagram.js` (async-тракт): `POST /{ig-user-id}/media` (image_url + caption) → poll статуса контейнера → `media_publish`.
4. Нормализатор: caption ≤2200, hook в первые ~125 симв, **без markdown**; ссылки в caption некликабельны — источник упоминать текстом или «ссылка в комментарии» (решить с владельцем на витрине первого поста).
5. Учёт лимита 100 API-публикаций/сутки (при 1–3 дайджестах/день — запас огромный, но счётчик в `publications` держать).
6. Тесты, деплой после санкции.

**Критерии приёмки:** дайджест уходит в IG как карточка + caption; контейнер-poll отрабатывает; media-URL живой на момент публикации; обложка генерируется без ручных шагов.

## 4. Сквозные вопросы (решить по ходу, не блокеры старта)

- **В-1. Open-core граница:** новые паблишеры — в публичную часть (`src/services/publishers/`) или в pro (`src/pro/`)? Рекомендация: базовые паблишеры и фундамент — публично (продолжение имеющейся структуры), «умные» надстройки (генерация hook/обложек моделью) — pro. **Решение за владельцем.**
- **В-2. Автопубликация vs кнопка:** сейчас публикация ручная (кнопки по платформам). Автопостинг новых дайджестов во все включённые каналы — тумблер per-канал в настройках; вводить после стабилизации каждого канала.
- **В-3. n8n:** спек-§10 маппит тракты на n8n, но текущий пайплайн n8n не использует (инстансы на VPS — чужой проект). Рекомендация: **не вводить n8n**, тракты живут в Node-воркере — меньше движущихся частей. Если владелец хочет n8n — отдельное решение.
- **В-4. Hook-качество:** эвристический hook (первые строки) может быть слабым для X/Threads/IG. Апгрейд — генерация hook моделью на этапе сборки дайджеста (дешёвый вызов, отдельный тумблер). Предлагается после этапа 2, когда hook начнёт реально работать в лентах.
- **В-5. Модерация новых каналов:** модуль модерации покрывает FB+TG. X/Threads/IG-комменты — вне скоупа этого плана, отдельный трек pro-модуля.
