# Article Fetcher — архитектура и runbook

Пайплайн кладёт в базу только **URL** статей (Telegram-бот / расширение); полный
**текст** (нужный для генерации комментариев) добирает отдельный фетчер. Это
**единственный источник текста статей** — если фетчер стоит, новые дайджесты
постепенно пустеют.

> ⚠️ Этот механизм ломался несколько раз и стоил многодневных простоев. Прежде чем
> лезть в код — пройди «Быстрая диагностика» ниже.

**С 2026-07-19 фетчер работает НА СЕРВЕРЕ (VPS), а не на Маке.** Mac-путь
(`scripts/local-fetcher.js` + LaunchAgent) выгружен и оставлен только как аварийный
fallback. Основной путь — контейнер `news-server-fetcher` (см.
[../production/server-fetcher/](../production/server-fetcher/)).

## Как это работает (серверный фетчер, 2026-07-19+)

Контейнер `news-server-fetcher` на том же VPS, что и API, отдельным
docker-compose (`production/server-fetcher/docker-compose.yml`), **не** трогает
основной `news-digest`:

- Каждые `FETCH_INTERVAL_MS` (дефолт 5 мин) `scripts/server-fetcher.js` спрашивает
  у API (`BASE_URL=https://news.questtales.com`, публичный URL — как раньше Mac)
  статьи `status=new`/`error` без контента.
- Для каждой открывает страницу в **реальном headed Chrome** по **CDP**, ждёт
  гидрацию SPA, извлекает DOM (cheerio, те же селекторы, что и расширение), затем
  `PATCH /api/articles/:id` с `{title, content}` (Bearer `API_SECRET_KEY`).
- Мёртвый URL после `MAX_FETCH_ATTEMPTS` (5) провалов → статус `unfetchable`
  (не ретраится вечно).

### Слои

```
node loop ──CDP──▶ headed Chrome (Xvfb :99) ──SOCKS──▶ Cloudflare WARP ──▶ Perplexity/Cloudflare
   │
   └── прямой HTTPS ──▶ https://news.questtales.com   (API; НЕ через WARP)
```

Через WARP-прокси ходит **только Chrome**. Node-процесс достаёт API напрямую по
публичному URL — ровно как раньше делал Mac.

### Почему именно так (и почему НЕ иначе)

| Решение | Причина |
|---|---|
| **На сервере, не на Маке** | Устраняет главную боль: Mac-Chrome периодически всплывал и **воровал фокус**. На сервере физического экрана нет вовсе. |
| **Xvfb (виртуальный дисплей)** | Chrome нужен **headed** (см. ниже), но headed без экрана невозможен → даём виртуальный `:99`. Красть фокус конструктивно нечему. |
| **Cloudflare WARP (бесплатный)** | Perplexity за Cloudflare, который **скорит** клиента (репутация IP + fingerprint + поведение), а не банит IP бинарно. Одинокий IP датацентра скорится плохо. WARP даёт egress с «человеческой» consumer-репутацией → challenge проходит. Замер: 456 КБ реального контента, CF-маркер отсутствует, с этого же VPS. |
| **Headed, НЕ headless** | Headless режется challenge’ем «Just a moment…» (проверено). Реальный headed Chrome проходит. **Не переводить на `--headless`.** |
| **CDP, а не AppleScript** | Историческая причина (см. корневой кейс §A). CDP на своём порту детерминирован; AppleScript адресовал любой инстанс Chrome. |
| **Опрос гидрации, не фикс. sleep** | Perplexity рендерит статью **после** load-события; через WARP-прокси латентность выше и гидрация >10с. Фетчер ждёт, пока в основном контенте появится реальный текст (>1000 симв., до 18с), и только потом берёт HTML. Хватать по `loadEventFired` (~3с) через WARP → 0 символов. |
| **WARP egress hard-gate** | Если egress через WARP не поднялся — entrypoint **не** запускает Chrome и выходит (Docker рестартит). Иначе фетч пошёл бы через голый IP датацентра, все статьи упали бы в Cloudflare и сожгли бы свой attempt-cap → ложный `unfetchable`. |
| **Встроенный WebSocket** | CDP-клиент на глобальном `WebSocket` Node 20 (`--experimental-websocket`). Единственная внешняя зависимость — `cheerio`, пиненный в ту же версию, что уже в дереве приложения. |
| **Счётчик попыток** | `articles.fetch_attempts` + `unfetchable` после 5 реальных провалов. Успешный `PATCH` с контентом обнуляет счётчик. |

## Корневой кейс (полная история: с чем столкнулись и как решили)

Три отдельные проблемы, вскрытые последовательно. Все закрыты.

### A. «Chrome сам поднимается с одной статьёй каждые 5-10 минут» (Mac, AppleScript)

**Симптом:** периодически Chrome сам всплывает с одной и той же статьёй раз в 5-10
мин; дайджесты пустеют. Возвращалось 2-3 раза.

**Ложный диагноз (не повторять):** «выключена галка *Allow JavaScript from Apple
Events*». В профиле пользователя она **была включена**. Виноват был не пользователь.

**Истинный корень:** старый фетчер рулил Chrome через AppleScript
(`tell application "Google Chrome"`), который адресует **любой** запущенный
инстанс. Когда рядом крутился посторонний automation-Chrome (playwright-mcp,
десктопный ChatGPT — свой профиль с выключенными apple-events), AppleScript попадал
в него → `execute javascript` падал → 0 chars по **каждой** статье. Провал
извлечения не менял статус → те же URL переоткрывались **каждый цикл вечно**.

**Фикс:** перевод на CDP + собственный выделенный Chrome (детерминированный порт,
свой профиль) + счётчик `fetch_attempts→unfetchable`. *(коммиты `52ab272`,
`b97d45e`)*

### B. Фокус-стил остался даже после CDP

**Симптом (владелец, справедливо):** «проблема-то вернулась». Даже выделенный
offscreen-Chrome при сбое поднимал приложение и **воровал фокус**.
`--window-position=-3000,-3000` НЕ мешает фокусу при запуске приложения.

**Вывод:** пока Chrome живёт на Маке рядом с пользователем, риск фокус-стила
неустраним по конструкции. Единственное настоящее решение — **убрать Chrome с
Мака** на сервер под виртуальный дисплей.

### C. «На сервере нельзя — Cloudflare, датацентр-IP»

**Ложный ранний вывод агента (не повторять):** «на сервере не выйдет: нет браузера,
IP датацентра забанен Cloudflare, работает только на Маке». Владелец надавил
фактом: «мой сайт за Cloudflare открывается через бесплатный VPN Opera; миллиарды
людей ходят через VPN — Cloudflare не может резать любой VPN».

**Измерение (не декларация):** Cloudflare — не бинарный бан по IP, а
**конфигурируемый скор** (репутация IP + TLS/browser fingerprint + поведение).
Решает **репутация IP**: residential/consumer-VPN-адреса «полны людей» и проходят;
одинокий IP сервера — флагается. **Cloudflare WARP** (бесплатный consumer-VPN)
даёт именно человеческую consumer-репутацию.

**Подтверждение (с прода, дважды):** headed Chrome под Xvfb, через WARP-SOCKS →
**456 КБ** контента Perplexity, `Cloudflare marker: false`. Egress-IP менялся
`148.230.84.56` (прямой, режется) → `104.28.x.x` (WARP, проходит). Ни платного
прокси, ни residential — бесплатный WARP.

**End-to-end на проде (2026-07-19):** серверный фетчер забрал очищенную тестовую
статью → отрендерил через WARP+Chrome → извлёк **4583 символа** → `Sent to server`,
`Enriched: 1, Failed: 0`. Mac при этом выгружен и не участвует.

> Переносимый разбор этого класса задач (гейт = лестница допущений, а не стена;
> измеряй фактом; поднимайся по лестнице дешёвого-первым) — в
> `~/.claude/rules/human-presence-access.md`. Этот кейс — его боевое подтверждение.

|-----|-----------------|-----------|

| Разные реальные URL (не один «удачный») | 3 живые статьи обнулены → переналиты | 4928 / 5387 / 5463 симв., совпадает с оригиналами |

| WARP при рестарте | `compose restart` | регистрация переиспользуется из volume, egress поднимается |

| Сброс счётчика | статья успешно налита | `fetch_attempts` → 0 |

### Подмена контента на неразрешимом URL — и две защиты от неё

**Что происходит.** Несуществующий (или удалённый автором) `/page/`-слаг **не**
отдаёт 404 и не отдаёт пустоту. SPA отвечает `200` и рисует **текст другой,
ранее загруженной статьи** (не «трендовую заглушку» — источник в состоянии
браузера, а не на стороне Perplexity). Экстрактор честно достаёт этот текст, и
без защиты под нашей ссылкой сохранилась бы чужая статья — а затем ушла бы в
опубликованный дайджест. Порог `>100` символов тут бесполезен: наблюдавшиеся
подмены — 1000–3200 символов.

**Что этого НЕ лечит (измерено).** `Network.setBypassServiceWorker(true)` — 2 из
2 подмена осталась. Он же плюс `setCacheDisabled(true)` — 5 из 6 подмена
осталась. Отключение кэша и service worker проблему не снимает: подставляется
даже не обязательно предыдущая статья, а любая ранее загруженная.

**Разделители «живая статья vs подмена» (измерено, а не предположено).**

| Кандидат | Результат | Вывод |
|---|---|---|
| Совпадение токенов слага с текстом | **56 из 133** реальных статей дают 0 совпадений | негоден: контент по-русски, слаг английский → зарубил бы 42% статей |
| HTTP-статус документа | мёртвый `200`, живой `200` | негоден: SPA-catch-all |
| Какой селектор поймал контент | у обоих `article`/`markdown` нет, оба → `main` | негоден: DOM идентичен |
| `canonical`, `og:url`, `og:title`, `document.title` | у живых и мёртвых **идентичны** (`https://www.perplexity.ai/`, `Perplexity`) | негоден: метатеги статичны, слага не содержат |
| `__NEXT_DATA__` / ld+json | отсутствуют у всех | негоден: встроенного JSON нет |
| Длина main-текста | мёртвые 302–3203, живые 2894–5867 | негоден: диапазоны пересекаются |
| **Ссылки на другие `/page/`** | **0** на всех 6 мёртвых, **ровно 4** на 12 разных живых статьях за 3 месяца | **годен: разделяет без исключений** |
| **Дубликат контента в корпусе** | на 1454 статьях совпадение первых 300 символов дают 3 группы, и все 3 — загрязнение | **годен: 0 ложных срабатываний** |

**Защита 1 — фильтр в фетчере.** `relatedLinks === 0` → контент **не
сохраняется**, статье засчитывается неудачная попытка
(`fallback_page: no related-page links`), после `maxFetchAttempts` она уходит в
`unfetchable`. Сожжённая попытка на живой статье дешевле, чем чужая новость,
опубликованная под нашей ссылкой.

**Защита 2 — дубль-гвард на сервере.** `PATCH /api/articles/:id` отвергает
контент, первые 300 символов которого уже принадлежат **другой** статье: `409
{error:'duplicate_content', duplicateOf}`, контент не пишется, неудача
фиксируется тем же путём, что `/fetch-failed`. Работает независимо от фетчера —
ловит подмену, пришедшую любым путём. Повторный PATCH статье её же текстом
(нормальный ретрай) не блокируется.

**Исторический факт.** До этих защит в корпусе накопилось 6 статей с чужим
контентом, и все 6 попали в опубликованные дайджесты: Cloudflare-интерстишл
(апр), наш собственный дашборд (июн), чужая вкладка «New Tab» (апр),
Chrome-ошибка «This site can't be reached» (май). Все — эпоха Mac/AppleScript
(захват чужого окна Chrome). Серверный фетчер такого пока не порождал, но класс
ошибки в проде срабатывал и публиковался.

Смотреть отказы так (в БД, а не в логах — логи ротируются, а `docker logs` на
проде опасен):
`SELECT url, fetch_error, fetch_attempts, status FROM articles WHERE fetch_error IS NOT NULL ORDER BY updated_at DESC LIMIT 20;`

## Быстрая диагностика (при пустых дайджестах)

Диагностируй по слоям, снизу вверх — не чини верх, не исключив низ.

1. **Жив ли серверный фетчер:**
   `ssh news-vps 'docker ps --filter name=news-server-fetcher --format "{{.Status}}"'`
   → должен быть `Up …`.
2. **Логи (ВСЕГДА bounded — `docker logs` на этом хосте может ронять dockerd):**
   `ssh news-vps 'timeout 15 docker logs --since 10m news-server-fetcher'`.
   - `WARP egress IP: …` + `Chrome is up` + `Sent to server` → работает.
   - `FATAL: WARP proxy egress not working` → WARP не поднял egress; контейнер сам
     рестартнётся. Если циклит — проверь `--cap-add NET_ADMIN` / `/dev/net/tun`.
   - `Content too short (0 chars)` по ВСЕМ статьям → гидрация/Cloudflare (см. §C);
     проверь, что egress-IP не датацентровый.
   - `Chrome unreachable … exiting for container restart` → Chrome умер, Docker
     поднимет заново.
3. **Cloudflare-скор:** если по всем статьям пусто — убедись, что egress идёт через
   WARP (лог `WARP egress IP: 104.28.x.x`, не `148.230.…`).
4. **Прод-сторона:** роут жив —
   `curl -s -o /dev/null -w '%{http_code}' -X POST -H "Authorization: Bearer $KEY" https://news.questtales.com/api/articles/x/fetch-failed`
   → 404 (handler есть). Колонка есть — `PRAGMA table_info(articles)` содержит
   `fetch_attempts`.

## Fallback: Mac-фетчер (ВЫКЛЮЧЕН 2026-07-19)

`scripts/local-fetcher.js` + LaunchAgent `com.newsdigest.local-fetcher` — прежний
путь. **Выгружен** (`launchctl bootout gui/$(id -u)/com.newsdigest.local-fetcher`),
выделенный Chrome убит. Оставлен на случай, если серверный путь понадобится
временно подменить. Та же логика (CDP + `fetch_attempts`), но Chrome на Маке →
риск фокус-стила (кейс §B). **Держать выключенным, пока серверный фетчер жив.**

Ручной аварийный прогон одного цикла на Маке (если серверный путь недоступен):

```bash
cd news-digest-pipeline
export PATH="$HOME/.nvm/versions/node/v20.20.0/bin:$PATH"
NODE_OPTIONS=--experimental-websocket node scripts/local-fetcher.js
```

Снова включить LaunchAgent (только как временный fallback):

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.newsdigest.local-fetcher.plist
```

## Конфиг

| Переменная | Где | Значение |
|---|---|---|
| `BASE_URL` | прод `.env` (env_file фетчера) | `https://news.questtales.com` |
| `API_SECRET_KEY` | прод `.env` | Bearer; совпадает с прод-ключом |
| `FETCH_INTERVAL_MS` | compose `environment` | период цикла (дефолт 300000) |
| `FETCH_CHROME_PORT` | compose `environment` | debug-порт Chrome (дефолт 9333) |
| `WARP_PROXY_PORT` | compose `environment` | SOCKS-порт WARP (дефолт 40000) |
| `MAX_FETCH_ATTEMPTS` | прод `.env` (опц.) | провалов до `unfetchable` (дефолт 5) |

Требования контейнера: `--cap-add NET_ADMIN`, `--device /dev/net/tun` (для WARP),
volume `warp-identity` (персист регистрации WARP). Всё объявлено в
`production/server-fetcher/docker-compose.yml`.
